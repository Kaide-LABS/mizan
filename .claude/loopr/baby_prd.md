# Baby PRD

## TL;DR
For me — a single researcher who has since completed foundational halal-investing education via Musaffa — what becomes true: I have a correct, deterministic, auditable pipeline that (1) ingests real public SEC EDGAR fundamentals and Tiingo EOD total-return price/dividend data for a curated ~100-ticker US equity universe, (2) screens that universe against AAOIFI-style business-activity and 30/30/5 financial-ratio rules, producing a three-state Pure/Mixed/Non-compliant verdict with a full reason trace for every ticker, and (3) lets me backtest long-only, fully-funded, zero-leverage strategies against that screened universe -- including the compliance-flip -> forced-divestment -> purification state machine -- and get back a static report where every number carries its honesty caveats (look-ahead bias, survivorship bias, pending-scholarly-verification) structurally, not as a footnote.

## Acceptance criteria
- A third party (no knowledge of how it was built) could check each of these by running commands and inspecting output, with no judgment call required:

1. Run the ingest job for the curated ~100-ticker universe twice. Both runs produce identical cached raw EDGAR JSON files and identical cached Tiingo Parquet files on disk (byte-for-byte on the second run, since nothing re-fetches) -- this observably proves ingestion is replayable, not re-derived from a live call each time.

2. Run the screening command over the universe. It prints/exports exactly one of PURE, MIXED, or NON_COMPLIANT for every ticker (never a boolean, never a missing verdict), and each verdict is accompanied by a reason trace naming which screen (business-activity or which financial ratio) drove it and the actual value vs. threshold. Separately, opening `config/fiqh_params.py` (or its rendered output) shows every judgment-call parameter (denominator basis, denominator smoothing, the 30/30/5 thresholds, tier toggles, grace period, purification forks) each stamped `pending_scholarly_verification` with a non-empty source citation -- a third party can count these against MASTER_PRD.md §10's 11-row register and confirm 1:1 coverage.

3. Run a backtest over a synthetic or historical window containing at least one ticker that flips from compliant to non-compliant mid-simulation. The backtest's event log observably shows the state sequence HELD(compliant) -> HELD(non-compliant, grace) -> DIVEST, with the divestment timestamped at the configured next-rebalance boundary (not immediately, not skipped). The purification ledger produced alongside it shows a nonzero `purification_liability` entry attributable to that holding.

4. Open any generated HTML report. It contains, verbatim, the caveat strings for look-ahead bias, survivorship bias, and pending-scholarly-verification on every results section -- and attempting to call the report's render function without an explicit (even empty) caveat set raises an error rather than silently rendering, which a third party can verify by trying it.

5. Any backtest report displays two distinct, separately-labeled numbers -- gross return and net-of-purification return -- and they differ whenever the purification ledger for that run is nonzero (confirming purification is a side-ledger deduction, never silently netted into NAV).

Each of these is checkable by observing program output/artifacts on disk; none requires asking the builder "did you mean X to happen." Grounded in MASTER_PRD.md §11 (V1 Definition of Done) and §7.3/§8 (state machine, purification), and PHASE_1_SPEC.md §8 (acceptance-criteria pattern already established for Phase 1, extended here to the whole-project level).

## Scope edges
- **out**: Concrete, named scope edges, each tagged out/deferred with a reason:

1. [deferred, pending scholarly ruling] Short-selling, any derivative (options/futures/swaps), margin/leverage, and any interest-bearing mechanic. Reason: these require a muamalat scholar's structural-feasibility ruling before they can even enter a roadmap -- not "V2 features," permanently blocked until that ruling exists (MASTER_PRD.md §2 DEFERRED).

2. [deferred, values-position not yet resolved] High-frequency or daily-profit-seeking trading strategies of any kind, even fully long-only/unlevered ones. Reason: this is the contested slice of halal-investing values questions that has NOT been resolved by the Musaffa education completed so far -- only the baseline (long-only, halal-screened, no shorting/derivatives/leverage, hold-and-rebalance-cadence) position is close to settled-permissible. This edge is new relative to the old PRDs, which did not name it explicitly as a values boundary (see staleness note below).

3. [out, engineering scope] True point-in-time screening (filing-lag-corrected `as_of_date` resolution) and a survivorship-corrected historical universe snapshot. Reason: V1 accepts look-ahead bias and survivorship bias as documented, loudly-flagged simplifications rather than solving them now; both are deferred to V2 as a data-slicing change, not a re-architecture (MASTER_PRD.md §7.1-7.2, §12).

4. [out, scale threshold] Universe size beyond the curated ~100-ticker subset (i.e., no full S&P 500 in V1) and no non-US markets. Reason: a 100-ticker universe is small enough for the hand-verified business-activity map (§6.1) to stay honest; scaling to 500+ tickers turns that hand-verification into an unreviewable bottleneck, so it's explicitly a V2 scaling step (MASTER_PRD.md §4, §12).

5. [out, permanent -- not a "for now"] Any LLM or LLM-adjacent component anywhere in the compliance-determination path (screening, compliance-flip state machine, purification ratio lookups). Reason: this is a hard, non-negotiable boundary, not a scope edge that might later move -- a hallucinated compliance verdict is the worst possible failure mode for this system (MASTER_PRD.md §2, §13; reconfirmed as a locked constraint in this kickoff).

6. [out, V1] Any dashboard or live UI (no FastAPI service, no Next.js frontend); output is a generated static HTML + plots report only. Reason: this is a single-user batch research tool, not a service -- a live UI is solving a problem this project doesn't have (MASTER_PRD.md §9).

7. [out, V1] Capital-gains purification (only dividend-triggered purification is computed). Reason: Fork A explicitly defaults capital-gains purification OFF pending scholarly ruling; V1 computes dividends-only purification (MASTER_PRD.md §8, §10 register #9).

Staleness flag on edge 2: the old MASTER_PRD/ULTIMATE_PRD/PHASE_1_SPEC documents never named the HFT/daily-trading contested slice as its own scope edge -- they scoped everything around "long-only quarterly-rebalance backtesting" without distinguishing that this framing was ALREADY inside the settled-permissible zone, versus a values question that was still open at the time of writing. Now that the values position has resolved (baseline long-only is buildable; HFT-adjacent is not), this edge should be named explicitly going forward so a future request to add, e.g., daily-rebalance or intraday signals is recognized as crossing a values boundary, not just a performance tuning knob. -- user-stated

## Boundary
This build covers a personal, single-user, deterministic research pipeline for halal-constrained US equity investing: (1) replayable ingestion and caching of real SEC EDGAR fundamentals and Tiingo EOD total-return price/dividend data for a curated ~100-ticker universe; (2) an AAOIFI-style business-activity and 30/30/5 financial-ratio screening engine that emits a three-state Pure/Mixed/Non-compliant verdict with a reason trace per ticker, with every fiqh judgment call (denominator basis/smoothing, thresholds, tier toggles, grace period, purification forks) exposed as a visible, sourced, 'pending scholarly verification' parameter, separate from a small set of hardcoded, non-configurable permissibility invariants (long-only, fully-funded, zero cash yield, no derivatives, no LLM in the compliance path); (3) a from-scratch, long-only, fully-funded backtest engine over that screened universe, including the compliance-flip -> forced-divestment -> purification state machine as a first-class mechanic; and (4) a generated static HTML+plots report in which every number is structurally stamped with its active caveats (look-ahead bias, survivorship bias, pending-scholarly-verification), showing both gross and net-of-purification returns as distinct figures.

This build explicitly does NOT cover: live trading, real capital, or order routing of any kind; short-selling, derivatives (options/futures/swaps), margin/leverage, or any interest-bearing mechanic (deferred pending a muamalat scholar's structural-feasibility ruling); high-frequency or daily-profit-seeking trading strategies of any kind, even fully long-only ones (deferred pending further education -- this is a values question not yet resolved, distinct from the baseline long-only position that is settled enough to build now); true point-in-time (filing-lag-corrected) screening or a survivorship-corrected historical universe snapshot (V1 accepts and loudly flags both biases instead of solving them); any universe beyond the curated ~100 US tickers, and no non-US markets; any LLM or LLM-adjacent component anywhere in the compliance-determination path, ever, as a permanent architectural boundary rather than a temporary scope limit; any dashboard, live UI, or backend service (FastAPI/Next.js) -- output is a static generated report only; and capital-gains purification (V1 computes dividend-triggered purification only).

This is a DRAFT boundary proposal for confirmation or tweaking -- it reflects only what has been stated in the confirmed problem statement, acceptance criteria, and scope edges above, and introduces no new scope of its own.
