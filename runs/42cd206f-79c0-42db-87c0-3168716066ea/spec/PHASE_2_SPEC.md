# Phase 2 — Crypto Ingestion, Candles Store & 24/7 Clock

## Goal
Build the keyless, public, Coinbase-primary / Kraken-fallback daily OHLCV ingestion path for the locked 14-token universe (`mizan.crypto.universe.CRYPTO_UNIVERSE`); a new granularity-agnostic `candles` table in the shared DuckDB store, additive alongside the existing equity `price_bars`/`fundamentals_facts` tables; raw-cache persistence of every fetched response (reusing `mizan/data/raw_cache.py` as-is); and the 24/7 UTC market clock that gives the crypto path a gap-free calendar, structurally distinct from the equity path's implicit trading-day assumption. This phase also closes four correctness gaps the Phase 1 review found unimplemented in Phase 1's own "Implications"/"Red-team findings" sections, before any new code builds on top of the invariant/no-najsh surface those gaps concern. No screening, no backtest wiring, no CLI pipeline verb, no report.

## Scope
In scope: a Part A0 backfill (test-only, plus the one-line `ResolvedOrder` guard R4 needs) closing Phase 1's open findings; `mizan/data/db.py` (extend, additive only); new `mizan/crypto/models.py`; new `mizan/crypto/ingest_coinbase.py`; new `mizan/crypto/ingest_kraken.py`; new `mizan/crypto/clock.py`; a new dated entry in `docs/modernization_log.md` re-verifying the `duckdb` pin; `docs/crypto/PHASE_2_SPEC.md` (commit this spec as the new governing document); and their tests. Out of scope: everything in "Out of scope for this phase" below.

Every new/edited module: `from __future__ import annotations` where the repo uses it, full type annotations (`mypy --strict` clean), ruff-clean, module docstring citing `docs/crypto/PHASE_2_SPEC.md §…`. No new runtime dependency — `httpx==0.28.1` and `duckdb==1.5.5` are both already pinned and reused as-is (see A1.0 on the `duckdb` re-verification).

### A2. The candle row shapes
**File:** `mizan/crypto/models.py` (new).
- `class CandleBar(MizanBaseModel)`: the normalized, exchange-agnostic write-shape every ingestion module produces before a DB insert.
  - `exchange: str` — `"coinbase"` or `"kraken"` (closed in practice, kept `str` rather than a `StrEnum` so a third fallback source is a value change, not a schema change).
  - `symbol: str` — the universe ticker (e.g. `"BTC"`), **not** the exchange's own product/pair id (`BTC-USD`, `XBTUSD`) — the DB and every later phase (screening, backtest) work in universe-ticker space; exchange product-id mapping is internal to each ingestion module (A3/B1) and never leaks past it.
  - `granularity: str` — `"1d"` for this phase (see A4 on why `str`, not an enum, is the AC-3 mechanism).
  - `ts: datetime` — UTC, tz-aware, the bucket's OPEN instant (e.g. `00:00:00Z` for a daily bar), never a naive datetime (`ValueError` on a naive input via a `field_validator`, mirroring the repo's existing low tolerance for ambiguous time handling).
  - `open: float`, `high: float`, `low: float`, `close: float` — each `Field(gt=0.0)` (a zero/negative OHLC value is a malformed bar, not a real quote).
  - `volume: float = Field(ge=0.0)` — zero-volume bars are real (illiquid days) and must not be rejected.
  - `source: str = Field(min_length=1)` — the specific endpoint/provenance string (e.g. `"coinbase_exchange_api"`, `"kraken_ohlc_public"`), never just the exchange name — this is the fatwa-part-2 "every data source must be public/licensed" provenance trail a reviewer or future report can grep for.
- Two small, module-private parsing functions (not Pydantic models — both wire formats are bare positional arrays with no field names, so forcing a named model over them would invent names the source never sent):
  - `_parse_coinbase_row(row: list[float]) -> tuple[datetime, float, float, float, float, float]` — Exchange API candle row is `[time, low, high, open, close, volume]` (note the low/high/open/close order, **not** OHLC order); returns `(ts, open, high, low, close, volume)` in `CandleBar` field order, raising `ValueError` on a wrong-length row or a non-finite value (`math.isnan`/`math.isinf`).
  - `_parse_kraken_row(row: list[object]) -> tuple[datetime, float, float, float, float, float]` — Kraken OHLC row is `[time, open, high, low, close, vwap, volume, count]`; returns the same 6-tuple shape, ignoring `vwap`/`count`; same finite-value guard.
  - Both raise a shared `MalformedCandleRowError(ValueError)` (defined in this module) so both ingestion modules can catch one exception type.

### A3. Coinbase-primary ingestion
**File:** `mizan/crypto/ingest_coinbase.py` (new).
- Module-level product-id map: `_COINBASE_PRODUCT_IDS: dict[str, str] = {ticker: f"{ticker}-USD" for ticker in CRYPTO_UNIVERSE}` (every one of the 14 tokens trades against USD on Coinbase at the time of writing per the research survey; this is a plain dict, not a per-ticker override mechanism, because overriding it is exactly the Phase-1-deferred "exchange/product symbol mapping" this phase is now defining for the first time — keep it a single flat literal here, not a config surface).
- `_COINBASE_GRANULARITY_SECONDS: dict[str, int] = {"1d": 86400}` — the only granularity-parameter mapping this phase populates; see A4.
- `class CoinbaseProductNotFoundError(RuntimeError)` — raised when the Exchange API returns 404 for a product id; the caller (B2) treats this as "fall back to Kraken for this ticker," never as a hard ingestion failure.
- `def fetch_coinbase_candles(ticker: str, *, granularity: str, start: datetime, end: datetime, client: httpx.Client, cache_dir: Path) -> tuple[CandleBar, ...]:`
  - Looks up `_COINBASE_PRODUCT_IDS[ticker]` (raises `KeyError` — a ticker outside `CRYPTO_UNIVERSE` is a caller bug, not a runtime condition to catch) and `_COINBASE_GRANULARITY_SECONDS[granularity]` (raises `UnsupportedGranularityError(RuntimeError)`, defined in this module, if `granularity` is not `"1d"` — this is the literal mechanism of AC 3: the parameter exists and is threaded through every layer; only `"1d"` is actually wired to a real exchange mapping in this phase, exactly as PHASE_1_SPEC.md's AC-mapping table already anticipated for AC 3 — "interface present even though only daily data is fetched now").
  - Calls `GET https://api.exchange.coinbase.com/products/{product_id}/candles` with `granularity=86400`, pagination as a backward-walking loop over `start`/`end` in windows of at most 300 rows (the Exchange API's documented per-request cap), via the injected `httpx.Client` (never constructs its own client — matches `ingest_tiingo_eod`'s existing injected-client convention so tests use `httpx.MockTransport`, no real network call in any test).
  - Raises `CoinbaseProductNotFoundError` on an HTTP 404 response for the product id (checked once, before pagination begins — a product either exists or it doesn't, it does not start existing partway through a backfill).
  - Applies simple client-side throttling to stay at or under 10 req/s (a `time.sleep` between paginated calls is sufficient at this build's scale — 14 tokens × a handful of 300-row windows is nowhere near the burst ceiling; no token-bucket class is needed, unlike Tiingo's hour/day budget, because Coinbase's limit is a steady per-second rate with no daily/monthly cap to track).
  - After each page's HTTP response: writes the raw response bytes verbatim to the raw cache via `mizan.data.raw_cache.write_raw_json`/`cache_path(cache_dir=cache_dir, source="coinbase/candles", key=f"{ticker}_{granularity}_{window_start.isoformat()}_{window_end.isoformat()}")` (the untouched wire bytes, before any parsing — "prove what the data said", matching the existing raw-cache convention) — **then** parses every row via `_parse_coinbase_row` into a `CandleBar`.
  - Stops paginating once a page returns zero rows (reached the product's earliest available history) or `start` is reached, whichever comes first; does not assume a fixed lookback depth (research found none is documented).
  - Returns every parsed `CandleBar` across all pages, ascending by `ts`, deduplicated (Coinbase's window-walking can overlap at the boundary; de-dup on `(exchange, symbol, granularity, ts)` before returning — the DB's own `INSERT OR REPLACE` (B1) is a second, independent idempotency layer, not a substitute for not double-counting within one fetch's in-memory result).
- Respects `is_cached()`: before issuing any HTTP call for a given page window, check the raw cache first (same idempotent-replay convention as `ingest_tiingo_eod`); a fully-cached backfill makes zero network calls.

### A4. Why granularity is `str`, not a closed enum
Both Coinbase and Kraken's own granularity parameters are small closed sets today (Coinbase: 60/300/900/3600/21600/86400 seconds or a named enum; Kraken: 1/5/15/30/60/240/1440/10080/21600 minutes) — but baking either exchange's specific set into Mizan's own interface would make "support a new granularity" mean editing a `StrEnum` definition (a signature-adjacent change) rather than adding one dict entry. Keeping `granularity: str` on every public function in this phase, with `_COINBASE_GRANULARITY_SECONDS`/`_KRAKEN_GRANULARITY_MINUTES` (B1) as the only per-exchange translation tables, means the `candles` table schema, every function signature, the cache-path convention, and every call site are already granularity-agnostic **today** — extending to `"1h"` later is adding one dict row in each ingestion module (and, once Phase 4 needs it, a matching DB index consideration), never a refactor. This is the literal reading of AC 3's own stated bar: "interface present even though only daily data is fetched now."

### A5. The `candles` table
**File:** `mizan/data/db.py` (edit, additive only — do not touch `_FUNDAMENTALS_FACTS_COLUMNS`/`_PRICE_BARS_COLUMNS`/`_CREATE_FUNDAMENTALS_FACTS`/`_CREATE_PRICE_BARS`/their call sites in `ensure_schema`).
- `_CANDLES_COLUMNS: tuple[str, ...] = ("exchange", "symbol", "granularity", "ts", "open", "high", "low", "close", "volume", "source", "ingested_at")`.
- `_CREATE_CANDLES` DDL, same `CREATE TABLE IF NOT EXISTS` style as the existing two tables:
  ```sql
  CREATE TABLE IF NOT EXISTS candles (
      exchange    VARCHAR   NOT NULL,
      symbol      VARCHAR   NOT NULL,
      granularity VARCHAR   NOT NULL,
      ts          TIMESTAMP NOT NULL,
      open        DOUBLE    NOT NULL,
      high        DOUBLE    NOT NULL,
      low         DOUBLE    NOT NULL,
      close       DOUBLE    NOT NULL,
      volume      DOUBLE    NOT NULL,
      source      VARCHAR   NOT NULL,
      ingested_at TIMESTAMP NOT NULL,
      PRIMARY KEY (exchange, symbol, granularity, ts)
  )
  ```
  — one wide table for every granularity and every future data type that fits the OHLCV shape (research finding: this is the documented pattern, e.g. `vgi-ccxt`/`the-rule-and-compass`, for adding granularities without a migration); a genuinely different shape (order-book snapshots, trades) gets its own table later rather than widening this one, exactly as the research recommends.
- `ensure_schema` gains one more `con.execute(_CREATE_CANDLES)` + `_verify_columns(con, table="candles", expected_columns=_CANDLES_COLUMNS)` call, appended after the existing two — same `SchemaError` behaviour on a column-set mismatch, no behaviour change to the existing two tables' creation or verification.
- `def upsert_candles(con: duckdb.DuckDBPyConnection, bars: tuple[CandleBar, ...]) -> int:` (new function, same module) — writes every bar via `INSERT OR REPLACE INTO candles VALUES (...)` (DuckDB's documented `ON CONFLICT` shorthand against the declared `PRIMARY KEY`, per the research findings), returns the count written. One statement per bar is acceptable at this build's scale (14 tokens × a few years of daily bars is low thousands of rows, per the research's own sizing note) — do not add a bulk/batched path in this phase; note in a comment that batching is a Phase-2-and-later optimization, not a Phase-2 requirement, if row counts ever grow past the daily/14-token scale.

## Part B (second agent)
Depends on Part A0's and Part A's committed modules. Delivers Kraken fallback, the 24/7 clock, edge cases, integration, and docs.

### B1. Kraken fallback ingestion
**File:** `mizan/crypto/ingest_kraken.py` (new).
- Module-level pair map: `_KRAKEN_PAIRS: dict[str, str]` — resolved (not guessed) once per the research's own recommendation ("resolve each of the 14 tokens' Kraken pair name via AssetPairs/Assets first, don't hardcode guessed pair strings"). Implement as `def resolve_kraken_pair(ticker: str, *, client: httpx.Client) -> str:` which calls `GET https://api.kraken.com/0/public/AssetPairs` once (cached — see cache key below), parses the response's keys/`altname` fields to find the tradable USD pair for `ticker`, checks the pair's `status` field is a tradable state (not delisted/reduced-only), and raises `KrakenPairNotFoundError(RuntimeError)` if no match or the pair is non-tradable. Cache this lookup under `source="kraken/asset_pairs"`, `key="all"` (one shared cache entry, not one per ticker — it is a single call returning every pair) so repeated resolutions across the 14-token loop make at most one network call total.
- `_KRAKEN_GRANULARITY_MINUTES: dict[str, int] = {"1d": 1440}` — the Kraken-side counterpart to A4's mapping; same `UnsupportedGranularityError` behaviour for any other value.
- `def fetch_kraken_candles(ticker: str, *, granularity: str, client: httpx.Client, cache_dir: Path) -> tuple[CandleBar, ...]:`
  - Resolves the pair via `resolve_kraken_pair`, then `GET https://api.kraken.com/0/public/OHLC?pair=<pair>&interval=1440` (GET only — Kraken rejected POST to public endpoints from 1 Jan 2024, per the research; use `client.get`, never `client.post`, with no code path that could be switched to POST).
  - **Always drops the last row of the response array** before parsing — Kraken's own documentation states the last row is always the current, not-yet-closed candle regardless of `since`; a test (B2) proves this explicitly so the drop is not silently lost in a future edit.
  - Accepts that this endpoint returns at most 720 of the most recent candles regardless of any `since` value — does **not** attempt to page backward past that cap (there is nothing to page into); the function's docstring states this ~720-day (~2-year) ceiling explicitly, and the caller (B2) surfaces it as a documented data-availability limitation, not silently accepted as "full history."
  - Throttles to roughly 1 request/second (a single `time.sleep(1.0)` between the `AssetPairs` call and the `OHLC` call, and between tickers in the caller's loop, is sufficient at 14-token scale — no budget-tracking class needed, unlike Coinbase's higher-throughput path).
  - Writes the raw response bytes to the raw cache (`source="kraken/ohlc"`, `key=f"{ticker}_{granularity}"`) before parsing, same "prove what the data said" convention as A3.
  - Parses every (non-final) row via `_parse_kraken_row`, deduplicates on `(exchange, symbol, granularity, ts)`, returns ascending by `ts`.

### B2. The fallback-selection orchestrator
**File:** `mizan/crypto/ingest_coinbase.py` or a new small `mizan/crypto/ingest.py` (pick one; if a new file, keep it thin — it only sequences A3/B1, it owns no parsing or HTTP logic of its own).
- `def ingest_universe_candles(*, granularity: str, start: datetime, end: datetime, cache_dir: Path, con: duckdb.DuckDBPyConnection, client: httpx.Client) -> dict[str, str]:` — for every ticker in `CRYPTO_UNIVERSE` (sorted, deterministic order): attempt `fetch_coinbase_candles`; on `CoinbaseProductNotFoundError` (or an empty result after a successful call — "Coinbase lacks sufficient history" per the PRD's own fallback trigger), fall back to `fetch_kraken_candles` for that ticker's **entire** series (never blends per-date between the two sources for one ticker, matching the locked PRD assumption "where both have data, Coinbase candles are authoritative and sources are not blended within a single series"); calls `upsert_candles` with whichever source's bars were used; returns `{ticker: "coinbase" | "kraken"}` so the caller (and, later, Phase 6's survivorship/report layer) knows which source backed each ticker without re-deriving it.
- Any `UnsupportedGranularityError` from either leg propagates unchanged — this function does not catch or paper over a bad granularity request.
- A genuine network/HTTP failure (anything other than the documented 404-means-fallback case) propagates unchanged — this phase defines no new halt/retry taxonomy; that is out of scope (see below).

### B3. The 24/7 market clock
**File:** `mizan/crypto/clock.py` (new).
- `def generate_market_days(start_date: date, end_date: date) -> tuple[date, ...]:` — every calendar day from `start_date` to `end_date` inclusive, UTC, ascending, with **no** gap for weekends or any holiday. Pure function of its two arguments (mirrors `mizan.backtest.clock.generate_rebalance_dates`'s own purity), but structurally simpler: crypto has no quarter-boundary cadence concept in Phase 2 (that is Phase 4's rebalance-cadence wiring over the 24/7 calendar this phase only generates the calendar for).
- Module docstring states explicitly: the equity path's notion of "trading day" is never computed from a calendar at all — it falls out implicitly from whichever dates happen to have a `price_bars` row (`mizan.backtest.clock._resolve_trading_dates`), which already skips weekends/holidays only because Tiingo never has EOD data for them. The crypto path has the opposite property on purpose: every single calendar day is a valid market day, independent of which dates the `candles` table happens to have rows for, which is exactly what AC 13 means by "operates 24/7 (no trading-day/holiday gaps)." This module is the one place that property is asserted and tested, so a later phase wiring the crypto backtest loop has a single, named function to call instead of re-deriving "which dates count" from whatever rows exist.

### B4. Edge cases and error handling
**File:** `tests/test_crypto_ingest_coinbase.py`, `tests/test_crypto_ingest_kraken.py`, `tests/test_crypto_clock.py` (extend/new).

## Spec assumptions

Gaps found while writing this spec were resolved as follows (nobody was asked):

- Coinbase's two keyless candle endpoints (legacy-rebranded Exchange API vs. newer Advanced Trade public) are functionally redundant for this build; the Exchange API is chosen as primary because it needs no CDP project/account concept and has simpler optional start/end semantics — Advanced Trade is not wired as a second Coinbase-side fallback in this phase (adding it would be a straightforward future enhancement, not a current requirement).
- `symbol` in the `candles` table is the universe ticker, never an exchange product/pair id — this is a new design decision this phase makes (Phase 1 explicitly deferred "exchange/product symbol mapping" to this phase); the mapping tables (`_COINBASE_PRODUCT_IDS`, `_KRAKEN_PAIRS`) are internal module state, not a new config/register surface, because they are mechanical lookups with one correct answer today, not a fiqh judgment call or a permissibility invariant.
- "Sufficient history" (the PRD's fallback trigger "Kraken fallback for tokens/history Coinbase lacks") is operationalized narrowly as "Coinbase returned zero rows for the whole requested window" (via 404 or an empty-but-200 response) rather than any comparative length heuristic — matching the locked assumption that Coinbase, when it has any data at all, is authoritative and not blended with Kraken.
- Per-ticker earliest-available-date metadata (useful for the Phase 6 survivorship-bias warning) is a natural **byproduct** of `fetch_coinbase_candles`'s/`fetch_kraken_candles`'s backward-walking pagination (the earliest `ts` actually returned) but this phase does not build a dedicated report/summary artifact for it — `ingest_universe_candles`'s returned `{ticker: source}` map is the only summary output Phase 2 commits to; a fuller per-ticker date-range summary is left for Phase 6 to derive directly from `candles` via `SELECT ticker, MIN(ts), MAX(ts)` rather than threading a new return type through this phase.
- The `duckdb` pin stays at `1.5.5` by default per A1.0's stated decision rule; this spec does not pre-commit to the outcome of the agent's live `pip index versions duckdb` check, only to the decision procedure and the requirement that the result be logged.
- `httpx.Client` instances are always caller-constructed and injected (never built inside `mizan/crypto/ingest_*.py`), matching `ingest_tiingo_eod`'s existing convention — this phase defines no new httpx-client-construction/timeout/retry policy of its own; a later phase wiring a real CLI verb is where a shared client configuration (timeouts, retries, TLS version floor per the Coinbase/Kraken TLS-1.2 findings) belongs.
- The 24/7 clock module exists because the crypto path needs it *as a building block* for the Phase 4 backtest loop, but Phase 2 does not call it from anywhere else yet — it is intentionally an unconsumed, directly-tested pure function in this phase, the same relationship A3 (`mizan/crypto/universe.py`) had to the rest of Phase 1's code.

## Implications

Second-order consequences found by review of this spec. This section only adds to the spec; the locked PRD is unchanged.

### Additional acceptance criteria

S3. A test asserts that `upsert_candles` run against a row whose `(exchange, symbol, granularity, ts)` key already exists, but whose `close`/`volume` values differ (e.g. a corrected re-fetch), actually overwrites the stored values rather than silently keeping the old row — `INSERT OR REPLACE` is assumed, not proven, by A6's idempotency test, which only re-inserts byte-identical rows. _(correctness: A6/B5's idempotency tests only prove "re-running with the same data doesn't duplicate rows." They do not prove the REPLACE half of `INSERT OR REPLACE` actually fires — a bug that silently downgraded this to `INSERT OR IGNORE`-equivalent behaviour would pass every currently-specified test while quietly freezing the first-ever fetched value for a ticker forever, which is the opposite of what a correction/re-fetch needs.)_
S4. A test asserts that `generate_market_days` and the equity-era `mizan.backtest.clock.generate_rebalance_dates` are never imported into the same module from `mizan/crypto/`, keeping the two calendars structurally unreachable from each other's code paths rather than merely "currently distinct in practice." _(maintenance: nothing enforces that a future crypto module does not import the equity clock's rebalance-date generator "for convenience" — e.g. to reuse its quarter-boundary logic for a crypto rebalance cadence. That would silently reintroduce the equity trading-day assumption's cousin (calendar-quarter boundaries) into the crypto path through the back door, defeating AC 13's intent without any existing test noticing, since AC 13's own tests only check the NEW module's output, never that the OLD module stays unreferenced from the new one.)_

## Red-team findings

Weaknesses found by an adversarial review of this spec before it is built. This section only adds to the spec; the locked PRD is unchanged.

### Additional acceptance criteria

R5. A test feeds `fetch_coinbase_candles`/`fetch_kraken_candles` a response row containing a `NaN` or `Infinity` numeric value (valid JSON via `float('nan')`-producing fixtures, since Python's `json` module happily round-trips these even though strict JSON forbids them) and asserts `MalformedCandleRowError` is raised, not a `CandleBar` silently constructed with a `NaN` field. _(high, data-integrity: A2 states parsing "raises `ValueError` on ... a non-finite value" but no test in A6/B4 actually constructs a non-finite fixture — Pydantic's `float` type accepts `NaN`/`inf` by default (they are valid IEEE-754 floats), so without an explicit `isfinite` guard actually wired AND tested, a single corrupted upstream byte produces a `CandleBar` that passes every `Field(gt=0.0)` check (`NaN > 0.0` is `False` in Python, so `Field(gt=0.0)` DOES reject plain NaN — but `float('inf')` passes `gt=0.0` cleanly), persists into `candles`, and silently poisons every downstream mean/weight calculation in Phase 4's backtest with no error anywhere.)_
R6. A test asserts `resolve_kraken_pair` rejects (raises `KrakenPairNotFoundError`, does not silently proceed) a pair whose `AssetPairs` `status` field is anything other than the documented "online"/tradable value — not merely "absent from the response" — covering the specific case research flagged: a delisted or reduced-only pair that still APPEARS in `AssetPairs` with a non-tradable status. _(medium, data-integrity: B1 states the status check "raises ... if no match or the pair is non-tradable," but the spec does not enumerate which status string(s) count as tradable, leaving "non-tradable" to mean whatever the implementer happens to check for. Kraken's own docs distinguish `online` from `cancel_only`/`post_only`/`limit_only`/`reduce_only`/`delisted`-style states; a check that only looks for the string `"delisted"` would silently ingest stale data from a `reduce_only` pair that is functionally no longer freely tradable, which matters for a halal spot-liquidity story even though it causes no code error.)_
R7. A test proves `ingest_universe_candles`'s per-ticker Coinbase-then-Kraken fallback does not partially write a ticker's `candles` rows if `fetch_coinbase_candles` succeeds, returns SOME rows, and then `upsert_candles` for that ticker raises partway through (e.g. a DB-level failure on one row) — either the whole ticker's batch commits or none of it does, never a partial row set silently left in `candles` with no record of which half is missing. _(medium, correctness: B2/B5 test the happy path and the full-fallback path, but not the "succeeded fetch, failed write" interleaving. `upsert_candles` (A5) is specified as one `INSERT OR REPLACE` statement per bar with no stated transaction boundary around a whole ticker's batch; without one, a mid-batch failure leaves `candles` holding, say, the first 40 of a ticker's 400 fetched days with no caveat/flag recorded anywhere that the series is truncated — exactly the kind of silent-partial-data failure MASTER_PRD.md §13 already names as this project's dangerous class for the equity side.)_
