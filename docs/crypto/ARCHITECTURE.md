# Phase 1 architecture

The single `Invariants` model is the permissibility boundary. `boot_check.check_all()` validates it and both fiqh registers before any later CLI work runs. Crypto adds `spot_only`, `synthetic_exposure_allowed`, and `lending_or_yield_allowed`; the existing fully-funded, margin, derivatives, and zero-cash-yield fields are reused.

`ResolvedOrder` is the no-najsh boundary. It is frozen and must contain a terminal fill or an explicit rejection. There is no pending, resting, open, or cancelable order representation, so an order without intent to fill is unrepresentable.

The crypto universe and fiqh register are new. The shared Pydantic base, invariant gate, caveat/result machinery, raw cache, database, backtest engine, and reporting layers are reused in later phases. Equity ingestion, AAOIFI screening, and EDGAR modules remain parked and importable.

The future signal-adapter seam is contract-only in Phase 1 and is planned for Phase 5. No HFT, live-trading, exchange-API-key, network-order, or signal-adapter implementation module exists under `mizan/`; `mizan/execution/intent.py` only defines terminal in-process value objects.

Phase 2 adds the granularity-agnostic `candles` table and a raw-cached daily OHLCV path. Each ticker is Coinbase-primary and falls back as a whole series to Kraken only when Coinbase returns no data; the two sources are never blended within one ticker. `mizan.crypto.clock.generate_market_days` treats every UTC calendar day as a valid crypto market day, unlike the equity path whose dates arise implicitly from available `price_bars` rows (see `docs/crypto/PHASE_2_SPEC.md` §B2/§B3).
Phase 3 uses one flat, hand-documented 23-entry token classification map rather than equity's two-layer SIC-plus-override design: crypto's curated classifications are already complete and have no external first-pass source. Only the memecoin category is gated by the configurable exclusion parameter; lending/riba and exchange margin/futures categories remain permanent rejects. The screen is pure in-memory logic and carries the pending scholarly-verification caveat.
Phase 4 adds a new, parallel `mizan/crypto/backtest.py` module rather than extending `mizan/backtest/`: `mizan.backtest.portfolio` and `mizan.backtest.strategy` are fully equity-agnostic and are reused as-is, but the equity rebalance clock and compliance-state machine are deeply equity-coupled (hardcoded quarterly cadence, a flip-grace-divest state machine crypto's static classification map gives nothing to observe) and are not reused. The crypto backtest's configurable-cadence rebalance-date generator runs over the 24/7 clock with a plain calendar-day offset, not a calendar-month snap. Per-side taker fee and slippage costs are baked directly into each traded leg's execution price before calling the reused, unmodified `apply_allocation`, rather than deducted from cash in a second step — this means every one of `apply_allocation`'s own non-negativity guarantees carries over to the cost-aware path unmodified. Both cost rates are structurally forbidden from being exactly zero at construction time.

Phase 5 adds `mizan/signal/`, a new top-level package alongside `mizan/execution/`, not a submodule of `mizan/crypto/` or `mizan/backtest/`: the signal-adapter contract is deliberately domain-agnostic infrastructure for a future two-speed prediction-plus-execution system, not a crypto-specific extension. `SignalAdapter` is a `typing.Protocol`, not an ABC, so a third-party adapter author satisfies the contract structurally without being forced into this repo's class hierarchy — unlike `mizan.execution.intent.ResolvedOrder`'s deliberately sealed order/outcome union. `Signal.outcome` reuses that same discriminated-union "illegal states unrepresentable" technique to keep a calibrated prediction and an abstention mutually exclusive by construction. `mizan/signal/validation_gate.py`'s `require_passing_gate` is a seam a future phase must call before letting any `Signal` drive a `Strategy`'s allocations — nothing in this repo calls it yet, and `GateCriteria`'s booleans are caller-attested placeholders, not a real calibration/baseline computation.

Phase 6 adds `Caveat.CUSTODY_FREEZE_RISK` as a fourth member of the shared `mizan.core.caveats.Caveat` enum rather than a crypto-local caveat type: the exchange-custody/freeze-risk fact is exactly the same kind of structural honesty disclosure the enum already exists to carry, and a second, parallel vocabulary would fragment the "no code path renders a number without its caveat set" guarantee across two incompatible types. `mizan/crypto/report.py` is a new, parallel module rather than a crypto-shaped reuse of `mizan.reporting.report.ReportInput`/`render_report`: `ReportInput` requires an 11-field equity `FiqhParams` and a `BacktestResult` with a populated `purification_ledger`, neither of which `CryptoFiqhParams` (4 fields) or `CryptoBacktestResult` (no ledger field) can satisfy. `mizan/cli/crypto.py` registers one `crypto-pipeline` verb, not four separate ones, matching the baby PRD's own "a single command that runs the full pipeline" acceptance criterion; it is also the one CLI entry point in the repo that opens DuckDB writably, since it is the one verb that performs its own ingestion.
